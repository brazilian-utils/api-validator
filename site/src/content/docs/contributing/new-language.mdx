The [parity matrix](/reference/parity/) shows every gap, and each [library page](/libs/python/) lists what that library is missing. Each gap is a self-contained contribution: the rule is written, the test cases exist, and in most cases an `implement` issue is already open in the library repository with the reference implementation and the cases inline.

## Adding a utility to an existing library

<Steps>

1. **Read the utility page.** The spec and the test cases are the whole behaviour. Other libraries' tabs show how they did it.

2. **Implement it** following the library's `CONTRIBUTING.md`. Name functions the way the language expects (`isValidCpf`, `is_valid_cpf`, `cpf.IsValid`…); the contract does not dictate names, the validator matches them by convention or by a binding in `libs/<lib>.json`.

3. **Register it in the library's harness.** The harness reads the vendored `api-contract/cases/*.json` and runs every case of every function it knows with the library's own test command.

4. **Add the usage section** in `docs/usage/<util>.md` ([usage files](/contributing/usage-files/)); `api-validator usage --scaffold` writes it from the cases you now pass.

5. **Release.** The issue closes by itself on the next api-validator run; the next site build shows your tab and status.

</Steps>

## Starting a library in a new language

<Steps>

1. Ask the organization for a repository under `brazilian-utils/<language>`.

2. In api-validator, add a language adapter (API extraction and a test runner) and `libs/brazilian-utils-<language>.json` with its `site` block (label, icon, install line, registry link). The guide is [docs/adding-a-language.md](https://github.com/brazilian-utils/api-validator/blob/main/docs/adding-a-language.md).

3. Start with the core functions: `api-validator issues --backfill core --lib <language> --apply` opens one issue per missing core function.

4. Adopt the harness ([docs/harness.md](https://github.com/brazilian-utils/api-validator/blob/main/docs/harness.md)) and ship `docs/usage/` from the first release.

</Steps>

<Aside type="tip">
Do not document differences from other libraries. If an implementation disagrees with the contract, that is a failing case to fix (or a contract change to propose), not a note to write.
</Aside>
