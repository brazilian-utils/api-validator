The spec of every utility is the contract in [api-validator](https://github.com/brazilian-utils/api-validator): one JSON file per domain with the functions, their signatures and the test cases every library runs. This site renders its pages from it, and a merged change opens an issue in every library that lacks the function.

## Anatomy

<FileTree>
- contract
  - _categories.json the sidebar groups
  - cpf.json title, summary, category, functions and their cases
  - cpf
    - spec.en.md long-form rule and algorithm, in English (optional)
    - spec.pt-BR.md the same, in Portuguese
    - references.md links to the official documents
</FileTree>

```json
{
  "$schema": "../schema/contract.schema.json",
  "domain": "cpf",
  "title": { "en": "CPF", "pt-BR": "CPF" },
  "summary": { "en": "One sentence under the page title.", "pt-BR": "Uma frase abaixo do título." },
  "category": "documents",
  "order": 1,
  "related": ["cnpj"],
  "functions": {
    "isValid": {
      "level": "core",
      "summary": "Whether the value is a valid CPF",
      "params": [{ "name": "value", "type": "string" }],
      "returns": "boolean",
      "tests": [
        { "args": ["82178537464"], "returns": true },
        { "args": ["00000000000"], "returns": false, "note": "reserved number" }
      ]
    }
  }
}
```

The keys of `functions` are the operation ids: the `##` headings in every library's [usage files](/contributing/usage-files/), and part of the function id (`cpf.isValid`) the validator, the issues and the status pages use. They are stable: renaming one is a breaking change for every library. `label` (`{ "en", "pt-BR" }`) overrides the operation name shown on the page when the default one does not fit. The full format, with every field, is in [docs/contract.md](https://github.com/brazilian-utils/api-validator/blob/main/docs/contract.md).

## Adding a function or a domain

<Steps>

1. Add the function (or a new `contract/<domain>.json`) with its signature and **test cases**: the cases are the spec every library is held to. Include the examples of the official rule and the edge cases (blank input, formatted input, wrong check digit).

2. For a new domain, write `spec.en.md` and `spec.pt-BR.md` when the rule needs more than the function descriptions (the algorithm, the regex), and list the official sources in `references.md`.

3. Run `npm run lint` (contract, schemas, formatting; `npm run api-validator fmt` fixes the formatting) and `npm run check -- --tests` to see which libraries already pass the new cases.

4. Open the PR. The pipeline comments the contract changelog and the issues it will open. When it merges, every library missing the function gets an `implement` issue, and the page appears on this site.

</Steps>

<Aside type="caution" title="Cases are the source of truth">
If the prose says formatted input is invalid, a case must expect `false` for it. The prose explains; the cases decide, and they are what the libraries run.
</Aside>

## Changing behaviour

Changing an expected value changes every library. Explain the change in the PR (the official source, which libraries it affects). Libraries that fail the changed cases get a `fix` issue automatically once it merges.
