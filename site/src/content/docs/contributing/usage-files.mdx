The spec, the signature and the test cases on every utility page come from the contract in [api-validator](https://github.com/brazilian-utils/api-validator). The code examples in the tabs do not: each library writes its own, in a folder of its repository.

<FileTree>
- python/
  - docs/
    - usage/
      - cpf.md
      - cnpj.md
      - license-plate.md
      - …
</FileTree>

The library owns those files. Whoever changes the API updates the usage file in the same pull request. This site only reads them.

## The format

One file per utility, named after the page slug (`cpf.md`, `license-plate.md`) or the contract domain (`licensePlate.md`). Inside, one `##` heading per operation, using the **operation id from the contract** (`contract/<domain>.json`, the keys of `functions`):

````markdown
## isValid

```python
from brutils import is_valid_cpf

is_valid_cpf('82178537464')  # True
is_valid_cpf('00011122233')  # False
```

## format

```python
from brutils import format_cpf

format_cpf('82178537464')  # '821.785.374-64'
```

## generate

```python
from brutils import generate_cpf

generate_cpf()  # random valid value
```
````

Rules:

- **Headings are contract operation ids**: `isValid`, `format`, `parse`, `removeSymbols`, `generate`, `getInfo`… Kebab case (`remove-symbols`) and the older `validate` resolve too. A heading that matches nothing is reported by `api-validator usage` and skipped by the build.
- **Each section shows the call**: import, call, result. A line of prose is fine ("network call, uses ViaCEP"). Do not explain the rule; the spec on the same page already does.
- **The example must call the lib's function.** The validator knows which native symbol implements each contract function and flags sections that never mention it.
- **Code and comments in English.** A `cpf.pt-br.md` next to it is shown to Portuguese readers when present.
- **`since` is optional**: a front matter field with the version in which the utility first shipped.
- **No section, no tab content.** The tab then says the lib does not implement the function, or that it does but has no example yet.

## Already have an API reference page?

Many libraries document every function on one page, one heading per function, named after the function itself. That page works as it is: declare it in `libs/<lib>.json` and the site cuts it into the usage tabs, mapping each heading (`### isValidCpf`) to the contract function the validator bound to that symbol.

```json
"usage": {
  "ref": "main",
  "reference": { "en": "docs/utilities.md", "pt-BR": "docs/pt-br/utilities.md" }
}
```

A section is everything down to the next heading: prose, options, edge cases, examples. Headings that are not a contract function (`## Conventions`, `## CPF`) are skipped; the text before the first function goes on the library's page as its **API conventions**. Usage files, when a library has both, win for the functions they cover. `api-validator usage --lib <lib> --materialize` writes a reference page out as usage files (the site's offline fallback, or the first step of a migration).

## Guides: bigger examples, with live demos

Some things are not one call: a form field that masks and validates as you type, an address form filled from the CEP, a state and city picker. Frontend readers need to see them working. A library can publish **guides**: Markdown pages whose examples come in tabs per framework, per variant and per file, each with an optional live demo.

```json
"usage": {
  "guides": { "en": "docs/guides", "pt-BR": "docs/pt-br/guides" },
  "root": "docs",
  "assets": ["docs/snippets"],
  "prepare": ["node", "scripts/examples.ts"]
}
```

Inside a guide, examples use this markup (the same one docsify renders, so the files can serve the library's own site too), one tag per line:

````markdown
<div class="example" data-name="React">

Prose about the React version.

<div class="variant" data-variant="CPF" data-demo="/snippets/live/?dir=cpf/react&example=cpf-field.tsx">

<div class="file" data-file="cpf-field.tsx">

[cpf-field.tsx](../snippets/cpf/react/cpf-field.tsx ':include :type=code tsx')

</div>

</div>

</div>
````

- `example` is a tab (a framework: React, Angular, Vue, Vanilla; or a library: Zod, Valibot). Readers pick one once and every guide follows.
- `variant` is an optional second row of tabs (CPF, CNPJ, CEP, Phone).
- `file` is one file of the example: an `:include` link to the file in the repository, or a fenced code block.
- `data-demo` on an example or variant is a page of the library, relative to `root`, shown running above the files. The folders in `assets` are copied to the site as they are, so the demo loads exactly the code the page shows. It reports its height with `parent.postMessage({ type: 'example-height', height }, location.origin)`.
- `prepare` runs in the checkout before anything is read (argv, no shell, no secrets), for libraries that generate their examples.

Links between guides stay on this site; a link to the reference page with a function anchor (`utilities.md#formatcpf`) goes to that operation here. The site finds which contract functions each guide calls and lists the guide on those utility pages.

## Try it

Every operation the reference implementation (JavaScript) has gets a **Try it** box, with no work from anyone: one input per contract parameter, prefilled with the first shared case, running the library's latest release in the browser. When the inputs are a shared case, it says whether the answer is the one the contract expects.

## Scaffolding the examples

Nobody has to write the first version by hand. The validator knows which functions the library implements and which shared cases it passes, and writes one section per undocumented function from those cases, in the library's language:

```sh
# in the library repo, after `check --tests` wrote its report
npx tsx <api-validator>/src/cli.ts check --lib python --path . --tests
npx tsx <api-validator>/src/cli.ts usage --lib python --path . --scaffold
```

Existing sections are never touched; new ones are appended. The results in the comments are the contract's expected values for cases the library passed, so the examples are true on the day they are written. Edit them freely afterwards.

`api-validator usage` without `--scaffold` prints what is documented, what is missing and what is wrong; `--strict` makes it fail, for a library CI that wants to enforce it.

## Which version is shown

The site reads the files at `usage.ref`: by default the library's **latest GitHub release**, so what readers see matches the package they install (repositories without releases fall back to the default branch). A library whose own docs already follow its main branch can set `"ref": "main"`. Until a library has its own `docs/usage/`, the site uses the copies in `site/fixtures/usage/<lib>/` of api-validator, in the same format: moving them into the library is a copy.

## Rebuilding the site on release

Add one step to the library's release workflow so the site rebuilds with the new version:

```yaml
- name: Notify the docs site
  if: success()
  run: gh api repos/brazilian-utils/api-validator/dispatches -f event_type=lib-released -f 'client_payload[lib]=python'
  env:
    GH_TOKEN: ${{ secrets.API_VALIDATOR_DISPATCH_TOKEN }}
```

Without it the site still rebuilds daily and on every contract change.

## Adopting it in a library

<Steps>

1. Copy `site/fixtures/usage/<lib>/` from api-validator into `docs/usage/` of the library (or run the scaffold command above).

2. Review the examples, add prose where it helps, and trim the README to installation, a couple of examples and a link to this site.

3. Merge and release. The next site build reads the files from the library.

</Steps>

<Aside type="note">
The site does not run the examples, but the values in scaffolded examples come from cases the library's own harness runs. When you write an example by hand, pick inputs from the contract cases and it stays true for the same reason.
</Aside>
