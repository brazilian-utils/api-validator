A spec de cada utilitário é o contrato no [api-validator](https://github.com/brazilian-utils/api-validator): um arquivo JSON por domínio com as funções, as assinaturas e os casos de teste que todas as bibliotecas rodam. Este site gera as páginas a partir dele, e uma mudança mergeada abre uma issue em cada biblioteca que não tem a função.

## Anatomia

<FileTree>
- contract
  - _categories.json os grupos da barra lateral
  - cpf.json título, resumo, categoria, funções e seus casos
  - cpf
    - spec.en.md regra e algoritmo por extenso, em inglês (opcional)
    - spec.pt-BR.md o mesmo, em português
    - references.md links para os documentos oficiais
</FileTree>

```json
{
  "$schema": "../schema/contract.schema.json",
  "domain": "cpf",
  "title": { "en": "CPF", "pt-BR": "CPF" },
  "summary": { "en": "One sentence under the page title.", "pt-BR": "Uma frase abaixo do título." },
  "category": "documents",
  "order": 1,
  "related": ["cnpj"],
  "functions": {
    "isValid": {
      "level": "core",
      "summary": "Whether the value is a valid CPF",
      "params": [{ "name": "value", "type": "string" }],
      "returns": "boolean",
      "tests": [
        { "args": ["82178537464"], "returns": true },
        { "args": ["00000000000"], "returns": false, "note": "reserved number" }
      ]
    }
  }
}
```

As chaves de `functions` são os ids de operação: os títulos `##` nos [arquivos de uso](/pt-br/contributing/usage-files/) de cada biblioteca, e parte do id da função (`cpf.isValid`) que o validador, as issues e as páginas de situação usam. São estáveis: renomear um quebra todas as bibliotecas. `label` (`{ "en", "pt-BR" }`) troca o nome da operação na página quando o padrão não serve. O formato completo, com todos os campos, está em [docs/contract.md](https://github.com/brazilian-utils/api-validator/blob/main/docs/contract.md).

## Adicionando uma função ou um domínio

<Steps>

1. Adicione a função (ou um `contract/<domínio>.json` novo) com a assinatura e os **casos de teste**: os casos são a spec que toda biblioteca precisa cumprir. Inclua os exemplos da regra oficial e os casos de borda (entrada vazia, entrada formatada, dígito verificador errado).

2. Para um domínio novo, escreva `spec.en.md` e `spec.pt-BR.md` quando a regra precisar de mais que as descrições das funções (o algoritmo, a regex), e liste as fontes oficiais em `references.md`.

3. Rode `npm run lint` (contrato, schemas, formatação; `npm run api-validator fmt` corrige a formatação) e `npm run check -- --tests` para ver quais bibliotecas já passam os casos novos.

4. Abra o PR. O pipeline comenta o changelog do contrato e as issues que vai abrir. No merge, cada biblioteca sem a função recebe uma issue `implement`, e a página aparece neste site.

</Steps>

<Aside type="caution" title="Os casos mandam">
Se o texto diz que entrada formatada é inválida, um caso precisa esperar `false` para ela. O texto explica; os casos decidem, e são eles que as bibliotecas rodam.
</Aside>

## Mudando comportamento

Mudar um valor esperado muda todas as bibliotecas. Explique a mudança no PR (a fonte oficial, quais bibliotecas afeta). Bibliotecas que falham nos casos alterados recebem uma issue `fix` automaticamente depois do merge.
