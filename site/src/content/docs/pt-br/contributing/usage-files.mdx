A seção "Uso" de cada página de utilitário não é escrita aqui. Ela é puxada, no build, de uma pasta dentro do repositório de cada biblioteca:

<FileTree>
- javascript/
  - docs/
    - usage/
      - cpf.md
      - cnpj.md
      - cep.md
      - license-plate.md
      - …
</FileTree>

A biblioteca é dona desses arquivos. Quem muda a API atualiza o arquivo de uso no mesmo pull request, e os revisores da própria biblioteca aprovam. Este site só lê.

## O contrato

Um arquivo por utilitário, com o nome do id da spec (`cpf.md`, `license-plate.md`…). Dentro, um título `##` por operação, usando os ids de operação do `meta.yaml` da spec:

````markdown
---
since: 2.0.0
---

## validate

```js
import { isValidCpf } from '@brazilian-utils/brazilian-utils';

isValidCpf('11144477735'); // true
isValidCpf('00000000000'); // false
```

## format

```js
import { formatCpf } from '@brazilian-utils/brazilian-utils';

formatCpf('11144477735'); // '111.444.777-35'
```

## remove-symbols

```js
import { parseCpf } from '@brazilian-utils/brazilian-utils';

parseCpf('111.444.777-35'); // '11144477735'
```

## generate

```js
import { generateCpf } from '@brazilian-utils/brazilian-utils';

generateCpf(); // um CPF válido aleatório
```
````

Regras:

- **Títulos são ids de operação.** `validate`, `format`, `remove-symbols`, `generate`, mais o que a spec declarar (`address-lookup`, `detect-format`…). Título desconhecido é ignorado e reportado no log do build.
- **Cada seção mostra a chamada.** Import, invocação, resultado. Uma ou duas linhas de texto são aceitáveis (por exemplo, "chamada de rede, usa ViaCEP"). Não explique a regra; a spec já faz isso.
- **Código e comentários em inglês.** O mesmo arquivo serve os dois idiomas do site. Se quiser uma versão em português, adicione `cpf.pt-br.md` ao lado; quando ela não existe, o arquivo em inglês é mostrado também para quem lê em português.
- **`since` é opcional.** A versão da sua biblioteca em que o utilitário entrou. Vira um badge.
- **Sem arquivo, sem aba.** Biblioteca sem `docs/usage/<util>.md` aparece como "ainda não disponível" naquele utilitário. Arquivo sem uma dada `## operação` mostra a mesma mensagem só naquela operação.

## Qual ref é usada

O site busca os arquivos na **última release do GitHub** da biblioteca, para que o leitor veja o mesmo que instala. Repositório sem release cai para o branch padrão.

## Mantendo os exemplos verdadeiros

O site não executa seus exemplos. Seu repositório deve, com o que sua linguagem usa para isso: `doctest` em Python, testes `Example` em Go, doc-tests em Rust, um arquivo Vitest que importa os mesmos trechos em JavaScript. Regra de bolso: se o exemplo no site está errado, o CI da biblioteca deveria ter ficado vermelho.

## Rebuild do site a cada release

Adicione um passo no seu workflow de release para o site reconstruir assim que a versão nova sair:

```yaml
- name: Notify docs site
  if: success()
  run: gh api repos/brazilian-utils/docs/dispatches -f event_type=lib-released -f 'client_payload[lib]=javascript'
  env:
    GH_TOKEN: ${{ secrets.DOCS_DISPATCH_TOKEN }}
```

`DOCS_DISPATCH_TOKEN` é um secret da organização com permissão para disparar workflows no repositório docs. Sem ele o site ainda reconstrói diariamente.

## Migrando um README existente

<Steps>

1. Crie `docs/usage/` no seu repositório.

2. Para cada utilitário que sua biblioteca implementa, crie `<id da spec>.md` e mova os exemplos correspondentes do README para seções `## operação`. É recorte e cola: os exemplos já existem.

3. Encurte o README para instalação, três exemplos e um link para este site.

4. Abra o PR. Quando ele for mesclado e a próxima release sair, as abas aparecem aqui automaticamente.

</Steps>

<Aside type="note">
Enquanto uma biblioteca não adota o contrato, este site monta as abas dela a partir de cópias temporárias guardadas em `fixtures/usage/` no repositório docs. Essas cópias já estão no formato certo; podem ir para o repositório da biblioteca como estão.
</Aside>
