A spec, a assinatura e os casos de teste de cada página vêm do contrato no [api-validator](https://github.com/brazilian-utils/api-validator). Os exemplos de código nas abas, não: cada biblioteca escreve os seus, numa pasta do próprio repositório.

<FileTree>
- python/
  - docs/
    - usage/
      - cpf.md
      - cnpj.md
      - license-plate.md
      - …
</FileTree>

A biblioteca é dona desses arquivos. Quem muda a API atualiza o arquivo de uso no mesmo pull request. Este site só lê.

## O formato

Um arquivo por utilitário, com o slug da página (`cpf.md`, `license-plate.md`) ou o domínio do contrato (`licensePlate.md`). Dentro, um título `##` por operação, com o **id da operação no contrato** (`contract/<domínio>.json`, as chaves de `functions`):

````markdown
## isValid

```python
from brutils import is_valid_cpf

is_valid_cpf('82178537464')  # True
is_valid_cpf('00011122233')  # False
```

## format

```python
from brutils import format_cpf

format_cpf('82178537464')  # '821.785.374-64'
```

## generate

```python
from brutils import generate_cpf

generate_cpf()  # random valid value
```
````

Regras:

- **Títulos são ids de operação do contrato**: `isValid`, `format`, `parse`, `removeSymbols`, `generate`, `getInfo`… Kebab case (`remove-symbols`) e o antigo `validate` também funcionam. Um título que não bate com nada é apontado pelo `api-validator usage` e ignorado no build.
- **Cada seção mostra a chamada**: import, chamada, resultado. Uma linha de texto ajuda ("chamada de rede, usa ViaCEP"). Não explique a regra; a spec na mesma página já explica.
- **O exemplo tem que chamar a função da lib.** O validador sabe qual símbolo nativo implementa cada função do contrato e aponta seções que nunca o mencionam.
- **Código e comentários em inglês.** Um `cpf.pt-br.md` ao lado, quando existe, aparece para quem lê em português.
- **`since` é opcional**: um campo de front matter com a versão em que o utilitário saiu.
- **Sem seção, aba sem conteúdo.** A aba então diz que a lib não implementa a função, ou que implementa mas ainda não tem exemplo.

## Já tem uma página de referência da API?

Muitas bibliotecas documentam todas as funções numa página só, um título por função, com o nome da própria função. Essa página serve do jeito que está: declare em `libs/<lib>.json` e o site a corta nas abas de uso, ligando cada título (`### isValidCpf`) à função do contrato que o validador associou àquele símbolo.

```json
"usage": {
  "ref": "main",
  "reference": { "en": "docs/utilities.md", "pt-BR": "docs/pt-br/utilities.md" }
}
```

Uma seção é tudo até o próximo título: texto, opções, casos de borda, exemplos. Títulos que não são função do contrato (`## Conventions`, `## CPF`) são ignorados; o texto antes da primeira função vai para a página da biblioteca como **convenções da API**. Quando a biblioteca tem os dois, os arquivos de uso vencem nas funções que cobrem. `api-validator usage --lib <lib> --materialize` escreve a página de referência como arquivos de uso (o fallback offline do site, ou o primeiro passo de uma migração).

## Guias: exemplos maiores, com demo ao vivo

Algumas coisas não são uma chamada só: um campo que aplica máscara e valida enquanto se digita, um formulário de endereço preenchido pelo CEP, um seletor de estado e cidade. Quem faz front precisa ver funcionando. Uma biblioteca pode publicar **guias**: páginas Markdown cujos exemplos vêm em abas por framework, por variante e por arquivo, cada um com uma demo ao vivo opcional.

```json
"usage": {
  "guides": { "en": "docs/guides", "pt-BR": "docs/pt-br/guides" },
  "root": "docs",
  "assets": ["docs/snippets"],
  "prepare": ["node", "scripts/examples.ts"]
}
```

Dentro de um guia, os exemplos usam esta marcação (a mesma que o docsify renderiza, então os arquivos também servem ao site da própria biblioteca), uma tag por linha:

````markdown
<div class="example" data-name="React">

Texto sobre a versão React.

<div class="variant" data-variant="CPF" data-demo="/snippets/live/?dir=cpf/react&example=cpf-field.tsx">

<div class="file" data-file="cpf-field.tsx">

[cpf-field.tsx](../snippets/cpf/react/cpf-field.tsx ':include :type=code tsx')

</div>

</div>

</div>
````

- `example` é uma aba (um framework: React, Angular, Vue, Vanilla; ou uma biblioteca: Zod, Valibot). O leitor escolhe uma vez e todos os guias seguem.
- `variant` é uma segunda fileira de abas, opcional (CPF, CNPJ, CEP, Telefone).
- `file` é um arquivo do exemplo: um link `:include` para o arquivo no repositório, ou um bloco de código.
- `data-demo` num exemplo ou variante é uma página da biblioteca, relativa a `root`, mostrada rodando acima dos arquivos. As pastas em `assets` são copiadas para o site como estão, então a demo carrega exatamente o código que a página mostra. Ela informa a altura com `parent.postMessage({ type: 'example-height', height }, location.origin)`.
- `prepare` roda no checkout antes de tudo ser lido (argv, sem shell, sem segredos), para bibliotecas que geram os exemplos.

Links entre guias ficam neste site; um link para a página de referência com âncora de função (`utilities.md#formatcpf`) vai para aquela operação aqui. O site descobre quais funções do contrato cada guia chama e lista o guia nas páginas desses utilitários.

## Teste

Toda operação que a implementação de referência (JavaScript) tem ganha uma caixa **Teste com JavaScript**, sem trabalho de ninguém: uma entrada por parâmetro do contrato, preenchida com o primeiro caso compartilhado, rodando a última release da biblioteca no navegador. Quando as entradas são de um caso compartilhado, ela diz se a resposta é a que o contrato espera.

## Gerando os exemplos

Ninguém precisa escrever a primeira versão na mão. O validador sabe quais funções a biblioteca implementa e quais casos compartilhados ela passa, e escreve uma seção por função sem documentação a partir desses casos, na linguagem da biblioteca:

```sh
# no repositório da lib, depois do `check --tests` gerar o relatório
npx tsx <api-validator>/src/cli.ts check --lib python --path . --tests
npx tsx <api-validator>/src/cli.ts usage --lib python --path . --scaffold
```

Seções existentes nunca são tocadas; as novas vão para o fim do arquivo. Os resultados nos comentários são os valores esperados pelo contrato em casos que a biblioteca passou, então os exemplos nascem corretos. Depois, edite à vontade.

`api-validator usage` sem `--scaffold` mostra o que está documentado, o que falta e o que está errado; `--strict` faz ele falhar, para uma CI de biblioteca que queira exigir.

## Qual versão aparece

O site lê os arquivos em `usage.ref`: por padrão a **última release no GitHub** da biblioteca, então o que se lê bate com o pacote instalado (repositórios sem release usam a branch padrão). Uma biblioteca cuja própria documentação já segue a branch principal pode usar `"ref": "main"`. Enquanto uma biblioteca não tem o próprio `docs/usage/`, o site usa as cópias em `site/fixtures/usage/<lib>/` do api-validator, no mesmo formato: levar para a biblioteca é copiar.

## Rebuild do site a cada release

Adicione um passo ao workflow de release da biblioteca para o site ser reconstruído com a versão nova:

```yaml
- name: Notify the docs site
  if: success()
  run: gh api repos/brazilian-utils/api-validator/dispatches -f event_type=lib-released -f 'client_payload[lib]=python'
  env:
    GH_TOKEN: ${{ secrets.API_VALIDATOR_DISPATCH_TOKEN }}
```

Sem isso o site ainda é reconstruído todo dia e a cada mudança no contrato.

## Adotando numa biblioteca

<Steps>

1. Copie `site/fixtures/usage/<lib>/` do api-validator para `docs/usage/` da biblioteca (ou rode o comando de scaffold acima).

2. Revise os exemplos, acrescente texto onde ajudar e enxugue o README para instalação, um ou dois exemplos e um link para este site.

3. Faça merge e release. O próximo build do site lê os arquivos da biblioteca.

</Steps>

<Aside type="note">
O site não executa os exemplos, mas os valores dos exemplos gerados vêm de casos que o próprio harness da biblioteca roda. Ao escrever um exemplo na mão, use entradas dos casos do contrato e ele continua correto pelo mesmo motivo.
</Aside>
